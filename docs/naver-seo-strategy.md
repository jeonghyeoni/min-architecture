## 0. 먼저 알아야 할 전제 — 네이버는 구글과 게임이 다르다

이 문서 전체를 관통하는 가장 중요한 사실부터 짚습니다.

**"용인 리모델링" 같은 지역+업종 키워드를 네이버에 검색하면, 화면 상단은
파워링크(광고) → 플레이스(지도) → 인플루언서/블로그 → VIEW 순으로 채워집니다.
자체 웹사이트가 노출되는 "웹사이트" 탭은 한참 아래에 있거나, 모바일에서는
스크롤을 여러 번 내려야 나옵니다.**

즉 사이트 코드를 아무리 완벽하게 최적화해도, 그것만으로 "용인 리모델링"
1페이지 상단에 뜨는 일은 일어나지 않습니다. 이건 기술력의 문제가 아니라
네이버 검색 결과 화면의 구조 문제입니다.

그래서 목표를 이렇게 나눠 잡아야 합니다.

| 목표 | 어디서 이기나 | 현실적 난이도 |
|---|---|---|
| "민건축" 검색 시 사이트가 최상단 | 웹사이트 탭 + 플레이스 | 쉬움 (1~2개월) |
| "처인구 집수리" 등 세부 지역어 | 플레이스 + 블로그 | 중간 (2~4개월) |
| "용인 리모델링" 등 대표 키워드 | **플레이스 + 블로그가 8할** | 어려움 (6개월+) |

**사이트 최적화는 "필요조건"입니다. 충분조건은 네이버 플레이스와 블로그입니다.**
이 문서는 사이트(1~2단계)를 먼저 끝내고, 플레이스·블로그(3~5단계)로
넘어가는 순서로 짜여 있습니다.

## 4. 이번 커밋에서 실제로 바꾼 것

### 🔴 치명적 버그 수정 — 모든 페이지의 제목이 동일했음

`BaseLayout.astro`가 `<title>`을 **하드코딩**하고 있었습니다.
각 페이지가 `title="프로젝트 | 민건축"` 같은 값을 넘기고 있었는데 레이아웃이
그 값을 아예 받지 않아 **전부 무시**되던 상태였습니다.

그 결과 홈, 시공사례, 문의, 모든 시공사례 상세 페이지가
같은 제목·같은 설명을 달고 있었고, 검색엔진 입장에서는 이게
**중복 콘텐츠**로 보입니다. 색인에서 대부분의 페이지가 제외되는 원인입니다.

→ 레이아웃을 props 기반으로 재작성해 페이지마다 고유한 제목·설명이 나가도록 수정.

### 그 외 적용 항목

| 항목 | 이전 | 이후 |
|---|---|---|
| 페이지별 title/description | ❌ 전 페이지 동일 | ✅ 전부 고유 |
| canonical | ❌ 없음 | ✅ 전 페이지 |
| og:image / og:url / og:type | ❌ 없음 | ✅ + OG 이미지 신규 제작 |
| 구조화 데이터 | ❌ 없음 | ✅ GeneralContractor, WebSite, Breadcrumb, FAQPage, Article, CollectionPage |
| Yeti/NaverBot 메타 | ❌ 없음 | ✅ |
| geo 메타 (지역 신호) | ❌ 없음 | ✅ |
| robots.txt | 기본형 | ✅ Yeti 명시 + 필터 파라미터 차단 |
| sitemap | 기본형 | ✅ priority/changefreq/lastmod |
| 홈 h1 | "작은 일 하나에도 최선을 다합니다" (**키워드 0개**) | ✅ 지역+공종 키워드 포함 |
| 이미지 alt | "전", "후", 제목만 | ✅ "지역 + 공종 + 시공사례" 서술 |
| FAQ | 4개, 구조화 없음 | ✅ 6개, 검색어 기반 + FAQPage 스키마 |
| NAP 일관성 | 페이지마다 표기 상이 | ✅ `src/lib/seo.ts` 단일 관리 |

### 코드 구조

사업자 정보·키워드·스키마 생성기를 **`src/lib/seo.ts` 한 곳**에 모았습니다.
주소나 전화번호가 바뀌면 이 파일만 고치면 사이트 전체(푸터, 문의 페이지,
구조화 데이터)에 동시 반영됩니다. 플레이스 정보와 어긋나는 사고를 막기 위한 구조입니다.

FAQ는 `src/data/faq.ts`에 두어 **화면 표시와 FAQPage 스키마가 같은 원본**을
쓰도록 했습니다. 둘이 어긋나면 검색엔진이 구조화 데이터를 통째로 무시합니다.

## 4-1. 도메인 이전 (민건축.com) — 반드시 읽을 것

### 한글 도메인은 Punycode로 써야 한다

`민건축.com`은 IDN(국제화 도메인)이라 실제 URL에서는 아래 형태로 변환됩니다.

```
민건축.com  →  xn--z69an80agjn.com
```

canonical, og:url, 사이트맵을 **한글 그대로** 쓰면 크롤러·메신저마다 인코딩이 달라져
같은 페이지가 여러 주소로 갈립니다. 그래서 코드에서는 전부 Punycode(ASCII) 형태로
통일했고, 사람에게 보여주는 자리에서만 한글로 표기합니다.

바꿔야 할 곳은 세 군데뿐입니다 (이미 적용 완료):

| 파일 | 값 |
|---|---|
| `astro.config.mjs` | `site: 'https://xn--z69an80agjn.com'` |
| `src/lib/seo.ts` | `SITE_URL` |
| `public/robots.txt` | `Sitemap:` 주소 |

### ❓ 서치어드바이저에 민건축.com을 재등록해야 하나?

**네, 반드시 새로 등록해야 합니다.**

네이버 서치어드바이저는 **도메인 단위로 사이트를 관리**합니다.
`min-architecture.vercel.app`으로 등록해 둔 것은 그 주소에만 적용되며,
`민건축.com`은 완전히 별개의 사이트로 취급됩니다. 등록하지 않으면 새 도메인은
사이트맵도, 수집 요청도 받지 못합니다.

또한 구글 서치콘솔의 '주소변경(Change of Address)' 같은 **공식 도메인 이전 도구가
네이버에는 없습니다.** 그래서 아래 절차를 직접 밟아야 합니다.

**절차**

- [ ] 서치어드바이저 → **사이트 등록**에 `xn--z69an80agjn.com` 입력
      (한글로 `민건축.com`을 입력해도 내부적으로 변환되지만, **Punycode로 넣는 편이 안전**합니다)
- [ ] 소유확인 — 코드에 `naver-site-verification` 태그가 이미 들어있어 통과됩니다
- [ ] **요청 → 사이트맵 제출**: `https://xn--z69an80agjn.com/sitemap-index.xml`
- [ ] **요청 → 웹페이지 수집**: 홈, `/services`, `/services/remodeling`,
      `/services/repair`, `/projects`, `/contact`
- [ ] **기존 vercel.app 사이트는 삭제하지 말 것.** 301 리다이렉트를 걸어두셨으니
      그대로 두면 기존에 쌓인 평가가 새 도메인으로 넘어갑니다. 지우면 그 연결이 끊깁니다
- [ ] 네이버 플레이스의 '홈페이지' 항목도 `민건축.com`으로 교체

> 301 리다이렉트를 이미 걸어두신 건 정확한 조치였습니다. 그 상태에서 새 도메인만
> 추가로 등록하시면 됩니다.

### ❓ 민건축.com을 이메일로 쓸 수 있나?

**기술적으로는 가능하지만, 한글 도메인 이메일은 권하지 않습니다.**

`문의@민건축.com` 같은 주소는 SMTPUTF8(EAI)이라는 규격을 양쪽 메일 서버가 모두
지원해야 주고받을 수 있는데, 국내외 상당수 메일 서버가 아직 제대로 지원하지 않습니다.
**고객이 보낸 메일이 반송되거나 조용히 사라질 수 있고**, 그게 견적 문의라면 손해가 큽니다.

현실적인 선택지는 셋입니다.

| 방식 | 비용 | 비고 |
|---|---|---|
| **네이버 웍스** | 무료 플랜 있음 | 국내 업체와 호환성 가장 좋음. 네이버 생태계와 연동 유리 |
| **구글 워크스페이스** | 유료 (월 약 7천원~) | 가장 안정적 |
| **Cloudflare Email Routing** | 무료 | 수신 전달만 가능(발신 불가). 임시방편 |

어느 쪽이든 **주소는 Punycode 형태(`xn--z69an80agjn.com`)로 설정**하시는 편이
호환성 문제를 피할 수 있습니다. 다만 그러면 고객에게 보여줄 때 주소가 흉해집니다.

**제 권고: 이메일용으로는 `mingeonchuk.com` 같은 짧은 영문 도메인을 하나 더 두시거나,
아예 이메일 없이 전화·네이버 톡톡으로만 받으세요.** 건축·집수리 업종 고객은
대부분 전화로 연락하지 이메일을 쓰지 않습니다.

> **현재 사이트에서는 이메일을 아예 제거했습니다.** `hello@minarchitecture.com`이
> 실제와 다르다고 하셔서, 틀린 연락처를 노출하는 것보다 없는 편이 낫다고 판단했습니다.
> 실제 주소가 정해지면 `src/lib/seo.ts`의 `BUSINESS`에 `email` 필드를 추가하면
> 푸터·문의 페이지·구조화 데이터에 한 번에 반영됩니다.
